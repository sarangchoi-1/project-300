## 1. 현재 상황

로그인, 회원가입, 가입 승인, 프로필, 그룹, 그룹 내 역할, 그리고 모든 권한 규칙까지
**완료됐고 테스트도 돌아갑니다.** 로컬에서 실행됩니다. 아직 실제 클라우드에는 올리지
않았고, Flutter 앱은 시작 전입니다.

`sarang` 브랜치에 SQL 마이그레이션 6개, 테스트 2세트, 레퍼런스 문서 3개가 있습니다.

---

## 2. 이것만은 모두가 이해해야 합니다

이 프로젝트에는 **백엔드 서버가 없습니다.** Java도 Node도 안 씁니다.

보통은 이렇습니다. **앱 → 우리 서버 → DB.** 여기서 서버가 문지기입니다. 누가 무엇을
볼 수 있는지 서버가 판단합니다.

Supabase는 이렇습니다. **앱 → DB.** Flutter 앱이 DB랑 거의 직접 HTTP로 통신합니다.

그래서 문지기가 **DB 안으로 들어와야** 합니다. 모든 권한 규칙을 SQL로 작성하고,
PostgreSQL이 직접 **RLS(Row Level Security)** 라는 기능으로 강제합니다.

> **이 부분은 꼭 소리 내서 설명하세요.** 중간에 우리 서버가 없기 때문에, 그 SQL
> 규칙들이 외부인과 우리 데이터 사이를 막는 **유일한** 장치입니다. 설치된 앱에서 API
> 키를 꺼내는 건 누구나 할 수 있습니다. 그건 정상이고 원래 그런 설계입니다. 안전한
> 이유는 오직 모든 테이블에 RLS가 켜져 있기 때문입니다. **RLS 없는 테이블은 전체
> 공개된 테이블입니다.**

그래서 Backend 2에게 자유롭게 하라고 하지 않고 지켜야 할 계약을 드렸습니다.

## 3. 무엇을 만들었나

테이블 3개입니다.

**`profiles`** — 유저 1명당 1행. 회원가입하는 순간 **자동으로** 생성됩니다.
`display_name`, `role`, `approval_status`를 가집니다. 비밀번호는 여기 없습니다.
Supabase Auth가 자기 테이블에 해시해서 따로 보관합니다.

**`groups`** — 소그룹(셀). 이름과 설명.

**`group_members`** — 누가 어느 그룹에 있는지, 그리고 그 그룹에서 `member`인지
`leader`인지.

전체를 움직이는 개념은 두 개입니다.

**역할(role)** — `member`, `leader`, `admin`. 무엇을 **할 수 있는지**.

**승인 상태(approval_status)** — `pending`, `approved`, `rejected`. **애초에 뭘 볼 수
있는지**. 모두 `pending`으로 시작합니다.

이 둘은 의도적으로 분리했습니다. 승인 안 된 admin은 아무 권한도 없고, 승인된 member는
정상적으로 씁니다.

몇 가지 규칙은 앱 코드가 아니라 DB가 직접 강제합니다. Flutter에 버그가 생겨도 뚫리지
않습니다.

- 한 유저는 **동시에 한 그룹만** 활성 상태로 속할 수 있습니다.
- 같은 유저를 같은 그룹에 두 번 넣을 수 없습니다.
- 그룹 이름은 중복될 수 없습니다.
- 그룹 리더 정보는 딱 한 곳에만 저장되므로, 서로 어긋날 수가 없습니다.

## 4. 누가 무엇을 볼 수 있나

읽기 권한입니다.

| | 비로그인 | 승인 대기 | 멤버 | 리더 | 관리자 |
|---|---|---|---|---|---|
| `profiles` | 없음 | 본인 것 | 본인 것 | 본인 것 | 전체 |
| `groups` | 없음 | 없음 | 본인 그룹 | 본인 그룹 | 전체 |
| `group_members` | 없음 | 없음 | 본인 것 | **그룹 명단 전체** | 전체 |

쓰기는 더 단순합니다. **관리자만 무엇이든 쓸 수 있습니다.** 아무도 스스로 그룹에
들어가거나, 나가거나, 자기 역할을 올리거나, 자기를 승인하거나, 그룹 이름을 바꾸거나,
남의 역할을 바꿀 수 없습니다. 리더는 명단을 **읽을** 수만 있고 수정은 못 합니다.

정책(policy) 14개에서 나온 결과이고, 테스트가 위 표의 모든 칸을 검증합니다.

## 5. 유저 입장에서의 흐름

Flutter 화면이 여기서 바로 나오기 때문에, 팀이 이 흐름에 합의해야 합니다.

1. 앱을 받아서 이메일, 비밀번호, 표시 이름으로 회원가입합니다.
2. 프로필이 자동 생성됩니다. 역할 `member`, 상태 `pending`.
3. 로그인은 된 상태지만, 앱이 아니라 **"승인 대기 중"** 화면을 봅니다. 데이터를
   찔러봐도 에러가 아니라 빈 목록이 옵니다.
4. 관리자가 대기 목록에서 이 사람을 보고 승인합니다.
5. 다음에 앱을 열면 들어갑니다. 세션이 폰에 저장되므로 로그인 화면 없이 자동
   로그인됩니다.
6. 관리자가 그룹에 넣어주고, 필요하면 그 그룹의 리더로 지정합니다.

3번을 주의해서 보세요. 승인 대기 유저도 **본인 프로필은 읽을 수 있습니다.** 의도한
것입니다. 앱이 대기 화면을 띄워야 할지 판단하는 방법이 이것입니다.

## 6. Flutter 개발자가 알아야 할 것

필요한 건 [FLUTTER_AUTH_INTEGRATION.md](./FLUTTER_AUTH_INTEGRATION.md)에 복붙 가능한
코드까지 다 있습니다. 지금 들어야 할 다섯 가지만 말하면,

**`supabase_flutter` 패키지를 쓰세요.** HTTP 클라이언트도, 직접 만든 API 레이어도
필요 없습니다. `supabase.from('profiles').select()`가 곧 API입니다.

**프로필을 직접 만들지 마세요.** `signUp(email:, password:, data: {'display_name':
...})`만 호출하면 됩니다. 프로필 행은 DB가 만듭니다. 애초에 직접 insert할 권한도
없습니다.

**자동 로그인은 공짜입니다.** `Supabase.initialize()` 후에
`supabase.auth.currentSession`을 읽으세요. null이 아니면 이미 로그인된 상태이고,
null이면 로그인 화면을 띄우면 됩니다.

**앱 전체를 `approval_status`로 막으세요.** 로그인 후 프로필을 가져와서 분기합니다.
`pending` → 대기 화면, `rejected` → 거절 화면, `approved` → 실제 앱. 대기 화면에서
빈 목록이 오는 건 에러가 아니라 **정상 동작**입니다.

**하루를 날릴 수 있는 함정 하나.** RLS가 update를 막으면 **에러가 나지 않습니다.**
HTTP 200에 빈 배열이 옵니다. 성공했을 때와 구분이 안 됩니다. 그래서 update나 delete에는
항상 `.select()`를 붙여서 행이 실제로 돌아왔는지 확인하세요.

```dart
final rows = await supabase.from('profiles')
    .update({'approval_status': 'approved'})
    .eq('id', userId)
    .select();

if (rows.isEmpty) {
  // 에러가 아니라, 그냥 권한이 없었던 것
}
```

## 7. Backend 2 개발자가 알아야 할 것

전체 내용은 [BACKEND2_RLS_CONTRACT.md](./BACKEND2_RLS_CONTRACT.md)에 있고, 그대로
가져다 고쳐 쓸 수 있는 `attendance`, `prayer_requests` 정책 예시도 들어 있습니다.

`bulletins`, `meetings`, `attendance`, `prayer_requests`, PDF 저장, 알림은 Backend 2
담당입니다. 신원, 그룹, 권한은 제가 담당입니다. 둘 사이의 인터페이스는 **헬퍼 함수**
입니다. `profiles`나 `group_members`에 직접 join 짜지 말고 이걸 쓰세요.

- `is_approved()` — 승인 대기 유저가 아무것도 못 보게, **모든** 읽기 정책에 넣으세요
- `is_admin()`
- `is_group_member(group_id)` — `meetings`처럼 그룹 단위 테이블에
- `is_group_leader(group_id)`
- `is_group_leader_of_user(user_id)` — `attendance`처럼 유저 단위 테이블에

왜 직접 join을 짜면 안 되냐면, 나중에 멤버십 구조를 바꿀 때 헬퍼로 만든 정책은 그대로
동작하지만 직접 짠 join은 조용히 깨지기 때문입니다.

반드시 지켜야 할 4가지입니다.

1. 외부에 노출하는 모든 테이블에 `enable row level security`. 예외 없습니다.
2. `force row level security`는 **절대 쓰지 마세요.** 헬퍼 함수는 소유자가 RLS를
   우회하는 것에 의존합니다. 강제로 켜면 무한 재귀가 생기고 DB의 모든 정책이
   망가집니다.
3. 모든 정책에 `to authenticated`를 쓰세요. 빼면 비로그인 사용자가 조용히 포함됩니다.
4. 유저 외래 키는 `auth.users(id)`가 아니라 `public.profiles(id)`를 가리키게 하세요.

작업이 끝나면 `back/supabase/tests/`에 케이스를 추가해 주세요. 멤버, **다른** 그룹의
리더, 승인 대기 유저, 비로그인 사용자가 모두 차단되는지 확인해야 합니다.

## 8. 오늘 정해야 할 것들

**a) 그룹 리더가 멤버 이름을 볼 수 있어야 할까요?** 지금은 못 봅니다. 리더는
`group_members`의 명단 행은 보지만 `profiles`에서는 본인 것만 봅니다. 그래서 출석
화면을 만들면 이름 없이 유저 ID만 보입니다. 일부러 좁게 만들고 팀 판단으로 남겼습니다.
*추천: 열어주는 쪽.* 정책 하나만 고치면 되고, Backend 2의 출석 화면에 필요합니다.

**b) 멤버가 자기 표시 이름을 수정할 수 있어야 할까요?** 지금은 안 됩니다. 본인 프로필
자체를 아예 수정할 수 없습니다. 요청이 나올 때까지 일부러 잠가뒀습니다. *추천: 표시
이름만 허용*, 나머지는 잠금 유지.

**c) 회원가입 시 이메일 인증을 받을까요?** 지금은 꺼져 있습니다. 관리자 승인이 이미
외부인을 막아주니, 인증은 주로 오타난 이메일이나 남의 이메일을 막는 용도입니다. 대신
Flutter 흐름이 바뀝니다. 켜면 링크를 누르기 전까지 `signUp`이 세션을 주지 않습니다.
*추천: MVP에서는 끈 채로 두기.*

**d) 첫 관리자를 누구로 하고, 배포는 언제 할까요?** 아직 클라우드에 아무것도 없습니다.
배포는 한 명의 승인이 필요하고, 첫 관리자는 앱에서 회원가입을 먼저 해야 승격시킬 수
있습니다.

## 9. 직접 돌려보기

Docker가 켜져 있어야 합니다. 그 다음,

```bash
cd back
supabase start          # 처음 실행 시 이미지 15GB 정도 받습니다
supabase db reset       # 마이그레이션 6개로 DB를 처음부터 만듭니다
```

띄운 다음 유용한 주소들입니다.

- Supabase Studio (테이블 보기, SQL 실행): `http://127.0.0.1:54323`
- Flutter 앱이 통신할 API: `http://127.0.0.1:54321`
- 발송된 메일 확인: `http://127.0.0.1:54324`
- `cd back && supabase status` — Flutter 앱에 넣을 키가 출력됩니다

뭔가 고친 뒤 깨진 게 없는지 확인할 때는,

```bash
back/scripts/verify-local.sh    # 1초 정도, Docker 필요 없음
back/scripts/verify-e2e.sh      # 스택이 떠 있어야 함, 실제 HTTP로 테스트
```

앞쪽은 SQL 테스트 10개 섹션을 돌립니다. 뒤쪽은 실제 회원가입, 실제 로그인 토큰, 실제
API를 거쳐 27개를 검사합니다. 멤버가 정말로 자기를 관리자로 못 만드는지도 여기서
확인합니다.

## 11. 나올 만한 용어

**RLS (Row Level Security)** — PostgreSQL이 행 단위로 당신이 그걸 볼/바꿀 권한이
있는지 판단하는 기능. 우리 권한 시스템 전체가 이것입니다.

**정책(policy)** — RLS 규칙 하나. 우리는 14개입니다.

**`auth.uid()`** — SQL 안에서 "지금 이 요청을 보낸 사람의 ID". 서명된 로그인 토큰에서
나오므로 위조할 수 없습니다.

**anon key** — 앱 안에 들어가는 공개 API 키. 원래 공개되는 게 정상이고, RLS가 켜져
있기 때문에만 안전합니다.

**service role key** — 모든 규칙을 우회하는 마스터 키. 서버에서만 씁니다. Flutter 앱에
절대 넣지 말고, 커밋도 하지 마세요. 현재 우리는 아무 곳에도 쓰지 않습니다.

**마이그레이션(migration)** — DB의 일부를 만드는 번호 붙은 SQL 파일. 한 번만 실행되고
DB가 실행 여부를 기록합니다.

**PostgREST** — 우리 테이블을 자동으로 HTTP API로 만들어주는 Supabase 구성 요소.
엔드포인트를 직접 안 만드는 이유입니다.

**Supabase Auth** — 회원가입, 로그인, 비밀번호를 담당하고 `auth.users` 테이블을 소유하는
구성 요소.
